# How Do You Secure a VPC Handling Sensitive Traffic?

When designing a VPC for a production application handling sensitive traffic, my primary goals are:

* Minimize the attack surface.
* Ensure only authorized communication between components.
* Prevent direct internet access to backend resources.
* Follow the Principle of Least Privilege.
* Design for both security and high availability.

In one of my projects involving an LLM application, we followed a layered security approach rather than relying on a single security mechanism.

The architecture looked like this:

```text
                    Internet
                        │
                        ▼
              Internet Gateway (IGW)
                        │
        ┌───────────────┴────────────────┐
        │                                │
 Public Subnet (AZ-1)            Public Subnet (AZ-2)
        │                                │
        ▼                                ▼
      ALB                         NAT Gateway
                                       │
──────────────────────────────────────────────────────────
             Private Application Subnets
──────────────────────────────────────────────────────────
        │
        ▼
 Haystack Application Servers (ASG)
        │
        ▼
    vLLM GPU Server
        │
   ┌────┴────┐
   ▼         ▼
Milvus    Embedding Service
```

Only the **Application Load Balancer** was exposed to the internet. Every backend component—including the application servers, GPU inference server, embedding service, and Milvus database—remained inside private subnets.

This significantly reduced the attack surface because users could never directly connect to the backend servers.

---

# Private Subnets

The most important security decision was placing all backend workloads inside private subnets.

That means:

* No public IP addresses.
* No direct SSH or RDP access from the internet.
* No inbound traffic from outside the VPC.
* Communication only through internal AWS networking.

Users could only reach the application through the Application Load Balancer.

Even if someone discovered the private IP address of an EC2 instance, they couldn't access it directly because there was no internet route.

---

# NAT Gateway Design

Although private instances shouldn't receive inbound internet traffic, they still need outbound internet connectivity for tasks such as:

* Downloading operating system updates.
* Pulling Docker images.
* Installing application packages.
* Sending logs and metrics to AWS services.

Instead of assigning public IP addresses, we used a **NAT Gateway**.

The NAT Gateway is deployed in a **public subnet** with an Elastic IP.

Private subnet route tables point their default route (`0.0.0.0/0`) to the NAT Gateway.

This provides:

* **Outbound internet access** for private instances.
* **No inbound internet access**, because the NAT Gateway does not accept unsolicited inbound connections.

For high availability, we deploy **one NAT Gateway per Availability Zone** and configure each private subnet to use the NAT Gateway in its own AZ. This avoids cross-AZ dependency and ensures outbound connectivity even if an AZ becomes unavailable.

---

# Security Groups

I consider **Security Groups** to be the primary security mechanism inside a VPC.

Security Groups are:

* **Stateful** firewalls.
* Attached directly to EC2 instances, ALBs, or other AWS resources.
* Allow-only rules (there are no explicit deny rules).
* Return traffic is automatically allowed.

Instead of allowing traffic from IP ranges, I prefer referencing other Security Groups.

For example:

### ALB Security Group

Allow:

* HTTP (80)
* HTTPS (443)

Source:

```text
0.0.0.0/0
```

---

### Haystack Security Group

Allow inbound traffic only from the **ALB Security Group** on the application port.

This means that even if another EC2 instance exists in the VPC, it cannot communicate with Haystack unless its Security Group is explicitly allowed.

---

### vLLM Security Group

Allow inbound traffic only from the **Haystack Security Group**.

No internet access.

No direct access from other workloads.

---

### Milvus Security Group

Allow inbound traffic only from the **Haystack Security Group** on the database port.

This ensures that only the application layer can query the vector database.

Using Security Group references instead of CIDR blocks provides tighter security and simplifies management as infrastructure scales.

---

# Network ACLs (NACLs)

While Security Groups secure individual resources, **Network ACLs** provide an additional layer of protection at the subnet level.

Unlike Security Groups, NACLs are:

* **Stateless**.
* Support both **Allow** and **Deny** rules.
* Evaluated in rule-number order.
* Applied to an entire subnet.

In most production environments, Security Groups handle day-to-day access control, while NACLs are used for broader subnet-level protections.

For example, if an organization wants to block traffic from a known malicious IP range before it even reaches EC2 instances, a NACL can deny that traffic at the subnet boundary.

So I use them as an additional defense layer rather than replacing Security Groups.

---

# Defense in Depth

Rather than relying on one control, we implement multiple layers:

* **Public Subnets** → Only ALB and NAT Gateway.
* **Private Subnets** → Application servers and databases.
* **Security Groups** → Control communication between services.
* **NACLs** → Subnet-level filtering.
* **IAM Roles** → Control AWS API permissions.
* **Encryption** → Encrypt EBS volumes, S3 buckets, and data in transit using TLS.
* **CloudTrail & VPC Flow Logs** → Audit API activity and network traffic for monitoring and investigations.

This layered approach means that even if one control is bypassed, additional security layers continue protecting the environment.

---

# Real Project Example

In our LLM infrastructure, users could access only the Application Load Balancer over HTTPS.

The Haystack application servers, vLLM GPU instances, embedding service, and Milvus database all resided in private subnets without public IP addresses.

Security Groups ensured that:

* Only the ALB could communicate with the Haystack application servers.
* Only the Haystack servers could access the vLLM inference service.
* Only the Haystack servers could communicate with the Milvus database.

Private instances used NAT Gateways for outbound internet access to download packages and send logs, while remaining inaccessible from the internet.

This design gave us a secure, highly available architecture that followed AWS networking best practices.

---

# Interview Summary

> "When securing a VPC handling sensitive traffic, I start by minimizing exposure. Only internet-facing components like the ALB are placed in public subnets, while application servers, GPU inference servers, and databases remain in private subnets without public IPs. Private instances access the internet through NAT Gateways for outbound traffic only. I use Security Groups as the primary access-control mechanism because they are stateful and allow me to define least-privilege communication between application tiers using Security Group references. Network ACLs provide an additional subnet-level security layer for broader allow or deny rules. Combined with IAM, encryption, and monitoring services like CloudTrail and VPC Flow Logs, this creates a layered, defense-in-depth security architecture suitable for production workloads."


# Cost Optimization Strategies I Applied

In my previous projects, cost optimization was always an important consideration because we were running applications on AWS, including an LLM-based platform where GPU instances were one of the largest contributors to infrastructure cost.

Whenever I think about cost optimization, I focus on three main areas:

1. **Right-sizing resources**
2. **Scaling resources based on demand**
3. **Choosing the appropriate pricing model**

---

# 1. Right-Sizing Infrastructure

One of the first things we did was select instance types based on the workload instead of using the same instance type for every component.

For example, in our LLM infrastructure:

* The **Haystack application layer** mainly handled API requests, request orchestration, communication with Milvus, and interactions with the inference service. Since this workload was CPU-intensive but did not require GPUs, we deployed it on general-purpose compute instances.

* The **vLLM inference layer** performed Large Language Model inference, which required GPU acceleration. Instead of allocating GPU instances to every service, we isolated GPU workloads to the vLLM layer and used GPU-enabled instances only where they were actually required.

* Supporting services like the **Embedding Service** and **Milvus** were deployed on instance types appropriate for their CPU, memory, and storage requirements rather than over-provisioning them.

This approach avoided paying for expensive compute resources where they were unnecessary.

---

# 2. Auto Scaling Based on Workload

The biggest cost optimization we implemented was Auto Scaling.

Instead of running the maximum number of instances all the time, we configured Auto Scaling Groups so the infrastructure expanded only when traffic increased.

For the Haystack application layer:

* Minimum Capacity: 2 instances
* Desired Capacity: 2 instances
* Maximum Capacity: 4 instances

During normal business hours, two instances were sufficient.

When traffic increased, CloudWatch monitored the **RequestCountPerTarget** metric from the Application Load Balancer.

If the request rate exceeded our threshold, the Auto Scaling Group automatically launched another Haystack instance.

When traffic reduced, unnecessary instances were terminated automatically.

This allowed us to maintain application performance during peak traffic while avoiding the cost of running additional instances 24/7.

---

# 3. Independent Scaling for GPU Infrastructure

GPU instances are significantly more expensive than standard compute instances.

Instead of scaling the entire infrastructure together, we separated the application layer from the inference layer.

This meant:

* Haystack servers scaled according to incoming request volume.
* GPU inference servers were evaluated separately based on inference capacity.

This prevented unnecessary GPU provisioning.

For example, if only the application layer experienced higher traffic but the GPU still had available capacity, we scaled only the Haystack servers rather than launching another expensive GPU instance.

That separation helped optimize infrastructure costs while maintaining application performance.

---

# 4. Monitoring Resource Utilization

Cost optimization is not a one-time activity.

We continuously monitored infrastructure utilization using CloudWatch and our monitoring dashboards.

We reviewed metrics such as:

* CPU utilization
* Memory utilization
* Request throughput
* Response latency

These metrics helped us identify underutilized resources and validate whether instance sizes were appropriate.

If we noticed consistently low utilization over a sustained period, we evaluated whether the workload could run on a smaller instance type.

Similarly, if utilization remained consistently high, we considered increasing instance size or adjusting the scaling policy.

---

# 5. Storage Optimization

We also selected storage based on application requirements.

Instead of allocating large, high-performance volumes everywhere, we provisioned storage according to workload needs and avoided unnecessary over-provisioning.

This helped reduce storage costs while maintaining required performance.

---

# 6. Spot Instances (Best Practice)

Although our production environment primarily used On-Demand Instances because of availability requirements, Spot Instances are an excellent cost optimization strategy for workloads that can tolerate interruptions.

Examples include:

* CI/CD build agents
* Batch processing
* Data analytics jobs
* Non-production environments
* Fault-tolerant Kubernetes worker nodes

Spot Instances can reduce compute costs significantly, but because AWS can reclaim them with short notice, I would avoid using them for critical production components unless the application is designed to handle interruptions gracefully.

---

# Real Project Example

A practical example from our LLM project was our Auto Scaling strategy.

Initially, it might seem reasonable to keep four Haystack servers running continuously to handle peak traffic.

However, our load testing showed that two servers comfortably handled normal traffic.

Instead of paying for four instances all day, we configured Auto Scaling to keep two instances running by default and add more only when CloudWatch detected sustained increases in traffic.

This approach reduced infrastructure costs during normal operations while ensuring enough capacity during peak demand.

Similarly, we treated GPU infrastructure separately because GPU instances represented the highest infrastructure cost. By scaling GPU resources independently, we avoided launching expensive instances unless they became the actual bottleneck.

---

> "The main cost optimization strategies I applied were right-sizing infrastructure, workload-based Auto Scaling, and separating scaling policies for different application tiers. In our LLM project, we selected instance types based on workload requirements instead of using GPU instances everywhere. We configured Auto Scaling Groups for the Haystack application layer using the ALB RequestCountPerTarget metric so that additional instances were launched only during increased traffic. We also treated the GPU inference layer as a separate scaling domain because GPU instances are significantly more expensive than standard compute instances. This approach allowed us to maintain application performance while optimizing infrastructure costs. For workloads that can tolerate interruptions, such as CI/CD runners or batch jobs, I would also consider using Spot Instances as an additional cost optimization strategy."
