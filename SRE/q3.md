# IAM: Role vs Policy vs Trust Relationship & Least-Privilege Lambda Access

## Part 1: Difference Between IAM Role, IAM Policy, and Trust Relationship
These three concepts are closely related, but they serve different purposes.

### 1. IAM Role
An IAM Role is an AWS identity that provides temporary permissions to a user, service, or application. Unlike an IAM User, a role does not have permanent credentials such as a username or password. Instead, it is assumed by a trusted entity when it needs to perform specific AWS operations.

Think of an IAM Role as a job position within an organization.
For example:
* A "Database Administrator" role allows database administration.
* A "ReadOnly Auditor" role allows only read access.
* A "Lambda Execution Role" allows a Lambda function to access AWS services.

The role itself doesn't define what actions are allowed. Those permissions come from policies attached to the role.

### 2. IAM Policy
An IAM Policy is a JSON document that defines what actions are allowed or denied on which AWS resources.

A policy answers three important questions:
* What actions are allowed?
* On which resources?
* Under what conditions?

For example, a policy might allow:
* Read objects from an S3 bucket.
* Write items into a DynamoDB table.
* Create CloudWatch logs.

Policies are attached to IAM Roles, IAM Users, or IAM Groups.



# ALB vs NLB – Interview Answer

Both **Application Load Balancer (ALB)** and **Network Load Balancer (NLB)** distribute incoming traffic across multiple backend servers, but they operate at different layers of the OSI model and are designed for different use cases.

The decision to use one over the other depends on the type of traffic, routing requirements, and performance expectations.

---

# Application Load Balancer (ALB)

An **Application Load Balancer** operates at **Layer 7 (Application Layer)**, which means it understands HTTP and HTTPS traffic.

Because it understands the contents of an HTTP request, it can make intelligent routing decisions based on:

* URL path
* Host name
* HTTP headers
* Query parameters
* Request methods

For example:

```text
https://example.com/api/users      → User Service

https://example.com/api/orders     → Order Service

https://example.com/images         → Image Service
```

A single ALB can route requests to different target groups based on these rules.

ALB also provides features like:

* Host-based routing
* Path-based routing
* SSL/TLS termination
* Sticky sessions
* WebSocket support
* Integration with AWS WAF
* Health checks
* Authentication with services like Amazon Cognito or OIDC

Because of these Layer 7 capabilities, ALB is commonly used for web applications and microservices.

---

# Why We Used ALB in Our LLM Project

In our LLM infrastructure, users accessed the application through an **Application Load Balancer**.

The architecture looked like this:

```text
Users
   │
   ▼
Application Load Balancer
   │
   ▼
Haystack Application Servers
   │
   ▼
vLLM GPU Server
```

The ALB distributed incoming HTTP requests across multiple Haystack instances running in an Auto Scaling Group.

One of the reasons we selected ALB was that it exposes useful CloudWatch metrics, particularly **RequestCountPerTarget**, which we used as the primary scaling metric for the Haystack application layer.

Since the application communicated over HTTP/HTTPS and we wanted intelligent routing, health checks, and integration with Auto Scaling Groups, ALB was the right choice.

---

# Network Load Balancer (NLB)

A **Network Load Balancer** operates at **Layer 4 (Transport Layer)**.

Instead of understanding HTTP requests, it forwards traffic based only on:

* TCP
* UDP
* TLS
* IP addresses
* Ports

It does not inspect URLs or HTTP headers.

Its primary goal is **high performance and very low latency**.

Because it operates at Layer 4, NLB can handle millions of requests with extremely low overhead.

Another important feature is that NLB preserves the client's source IP address, which is useful for applications that need to know the original client IP for logging, security, or access control.

---

# Typical NLB Use Cases

I would choose an NLB when:

* The application uses TCP or UDP instead of HTTP.
* Extremely low latency is required.
* The application needs to preserve the client source IP.
* Handling very large numbers of connections.
* Exposing databases or custom TCP-based services.
* Load balancing services like Kafka, Redis, MQTT brokers, or game servers.

For example, if I were deploying a high-performance TCP-based financial trading application where every millisecond matters, I would choose an NLB.

---

# Key Differences

| Feature                | ALB                                        | NLB                                   |
| ---------------------- | ------------------------------------------ | ------------------------------------- |
| OSI Layer              | Layer 7                                    | Layer 4                               |
| Protocols              | HTTP, HTTPS, WebSocket                     | TCP, UDP, TLS                         |
| Path-based Routing     | ✅ Yes                                      | ❌ No                                  |
| Host-based Routing     | ✅ Yes                                      | ❌ No                                  |
| SSL Termination        | ✅ Yes                                      | Limited TLS support                   |
| Client IP Preservation | Via headers like X-Forwarded-For           | Native source IP preservation         |
| Best For               | Web applications, REST APIs, microservices | High-performance TCP/UDP applications |

# Real-World Example

Suppose a company has an e-commerce platform.

The architecture might look like this:

```text
                    Internet
                        │
                        ▼
                 Application Load Balancer
                        │
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
 User Service     Product Service   Order Service
```

The ALB examines the URL and routes requests to the appropriate microservice.

Now imagine the same company also has an internal Redis cluster used for caching.

Redis communicates over TCP, not HTTP.

In that case, an NLB would be a better choice because it efficiently forwards TCP traffic without inspecting application-layer data.

---

# How I Decide Between ALB and NLB

My decision is based on the application requirements.

If the application is a web application or REST API and requires intelligent routing, SSL termination, WAF integration, or HTTP-aware features, I choose an **Application Load Balancer**.

If the application uses TCP or UDP protocols, requires very high throughput, low latency, or source IP preservation, I choose a **Network Load Balancer**.

In short:

* **ALB is optimized for application-aware routing.**
* **NLB is optimized for high-performance network traffic.**
