



## What are the foundation pillars of SRE?

### Interview-ready answer

"In my understanding, SRE is built around a few important principles.

The first is reliability and availability, where our goal is to ensure applications remain stable and accessible.

The second is automation, where we reduce repetitive manual activities by automating infrastructure provisioning, deployments, and operational tasks.

The third is monitoring and observability, where we continuously monitor application and infrastructure metrics to identify issues proactively.

The fourth is incident management, where we focus on detecting, responding to, and resolving production incidents, followed by root cause analysis.

The fifth is scalability and performance, ensuring applications can handle increasing workloads without affecting the user experience.

Finally, continuous improvement is also important. We learn from production incidents, reduce recurring issues, and continuously improve system reliability.

Overall, the objective of SRE is to balance system reliability with the speed of software delivery."

In my current project, since we are deploying LLM workloads using Haystack and vLLM on AWS, we focus on a few important SLIs and SLOs to ensure application reliability and performance.

Our primary SLIs are:

1. **Availability:** We monitor whether our application endpoints are available and responding to incoming requests.

2. **Request Success Rate:** We track the percentage of successful API requests against the total number of requests.

3. **Latency:** We monitor API response time, particularly the 95th and 99th percentile latency, to understand how quickly the application responds.

4. **Throughput:** We monitor the number of incoming requests the application can handle within a given time.

5. **LLM Inference Performance:** Since we are working with LLM workloads, we also consider Time to First Token and token generation speed.

Based on these SLIs, we define our SLO targets. For example, we can target 99.9% application availability, 99.5% request success rate, and keep API latency within agreed thresholds for a defined workload.

We use Prometheus, Grafana, and CloudWatch to monitor these metrics and configure alerts whenever there is a deviation from the expected thresholds.

We also monitor CPU, memory, and GPU utilization to understand resource consumption and identify scaling requirements.

For example, when incoming request traffic increases, we monitor request count per target and use that information to scale our Haystack and vLLM infrastructure.

Our overall objective is to maintain application availability, minimize request failures, and provide consistent response times even during increased traffic.


## What is the difference between Monitoring and Observability?

### Interview-ready answer

"In my understanding, monitoring and observability are closely related, but they serve different purposes.

Monitoring is about continuously tracking predefined metrics of our applications and infrastructure to identify issues. For example, we monitor CPU utilization, memory utilization, application availability, request latency, and error rates using Prometheus and Grafana. We also configure alerts whenever these metrics cross certain thresholds.

Observability goes a step further. It helps us understand why an issue is happening by analyzing metrics, logs, and distributed traces.

For example, if we receive an alert that application latency has increased, monitoring helps us identify the performance degradation. Using observability, we can investigate application logs and distributed traces to identify whether the issue is related to a database query, an external API, or one of our microservices.

So, monitoring helps us detect problems, whereas observability helps us investigate and understand their root causes."
