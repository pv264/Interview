# How Would You Troubleshoot a High CPU Utilization Issue?

Whenever I receive an alert for high CPU utilization, I don't immediately restart the server or scale the infrastructure. My first objective is to understand whether the issue is temporary, infrastructure-related, or caused by the application.

I follow a structured troubleshooting process.

---

# Step 1 – Detection

Usually, the issue is detected through our monitoring system.

For example, Prometheus and Grafana may show CPU utilization consistently above 80% for more than 10 minutes, and Alertmanager sends a notification to Slack or email.

The first thing I verify is whether this is a genuine issue or just a temporary spike.

If CPU briefly reaches 90% for a few seconds and then returns to normal, I generally continue monitoring.

If it remains high for several minutes and users start reporting slow response times, I begin a detailed investigation.

---

# Step 2 – Identify Which Server Is Affected

First, I identify which server or pod has high CPU utilization.

For an EC2 instance:

```bash
top
```

or

```bash
htop
```

For Kubernetes:

```bash
kubectl top pods

kubectl top nodes
```

This tells me whether the issue is affecting one application, one node, or the entire cluster.

---

# Step 3 – Identify Which Process Is Consuming CPU

If it's an EC2 server, I use:

```bash
top

ps -eo pid,ppid,cmd,%cpu --sort=-%cpu
```

This helps identify which process is consuming the most CPU.

For example:

```text
Java Process

95% CPU
```

Now I know the application is responsible.

If another process such as backup software or antivirus is consuming CPU, the investigation follows a different path.

---

# Step 4 – Correlate with Application Metrics

CPU alone doesn't tell the full story.

I check Grafana dashboards for:

* Request rate
* Response time
* Error rate
* Memory utilization

I ask questions such as:

* Did traffic suddenly increase?
* Was a new deployment performed?
* Are users reporting slow responses?
* Is the application returning HTTP 5xx errors?

This helps determine whether high CPU is caused by increased workload or by an application problem.

---

# Step 5 – Check Application Logs

If the application process is consuming CPU, I review the logs.

I'm looking for:

* Infinite loops
* Repeated exceptions
* Database retries
* API retry storms
* Excessive background jobs

For Kubernetes:

```bash
kubectl logs <pod-name>
```

For Linux:

```bash
journalctl

or

tail -f application.log
```

Logs often reveal the underlying issue.

---

# Step 6 – Check Recent Changes

If CPU suddenly increased, I check whether anything changed recently.

Questions I ask include:

* Was a new version deployed?
* Were application configurations changed?
* Was a feature flag enabled?
* Was there a sudden increase in traffic?
* Did a scheduled batch job start?

Many production issues are linked to recent changes.

---

# Step 7 – Decide on Mitigation

The solution depends on the root cause.

### Case 1 – Genuine Traffic Increase

If CPU is high because user traffic has increased, I scale the application.

For example:

* Increase the number of application instances.
* Increase Kubernetes replicas.
* Trigger the Auto Scaling Group.

---

### Case 2 – Application Bug

If the logs show an infinite loop or inefficient code, I:

* Roll back to the previous stable version if needed.
* Work with developers to fix the issue.
* Deploy the corrected version after testing.

---

### Case 3 – Resource Undersized

If monitoring shows the application consistently runs at high CPU even under normal load, I evaluate:

* Right-sizing the EC2 instance.
* Increasing CPU requests and limits (for Kubernetes).
* Optimizing the application's performance.

---

# Step 8 – Verify

After implementing the fix, I verify:

* CPU utilization has returned to normal.
* Response time has improved.
* Error rate has reduced.
* Users can access the application successfully.

Only after confirming these checks do I close the incident.

---

# Prevention

After the incident, I focus on preventing recurrence.

Possible improvements include:

* Tuning Auto Scaling thresholds.
* Optimizing application code.
* Adding caching where appropriate.
* Configuring better alerts.
* Performing load testing before major releases.
* Reviewing resource sizing based on historical usage.

The goal is not just to resolve the incident but to reduce the chance of it happening again.

---

# Real Project Example

In our LLM infrastructure, we learned that CPU utilization wasn't always the best indicator of application load. During load testing, the Haystack application spent a significant amount of time waiting for Milvus and the vLLM inference server. CPU remained moderate even as request queues grew. Instead of relying only on CPU-based Auto Scaling, we switched to **ALB RequestCountPerTarget**, which better reflected actual demand. This improved scaling decisions and maintained application performance during traffic spikes.

# Troubleshooting Flow

```text
Alert Received

↓

Confirm CPU is consistently high

↓

Identify affected server or pod

↓

Identify high-CPU process

↓

Check traffic and application metrics

↓

Review application logs

↓

Check recent deployments or changes

↓

Find root cause

↓

Apply the appropriate fix

↓

Verify recovery

↓

Implement preventive measures
```

---

# Interview Summary

> **"When I receive a high CPU alert, I first confirm that it's not a temporary spike. Then I identify the affected server or pod and determine which process is consuming CPU using tools like `top`, `htop`, or `kubectl top`. Next, I correlate CPU usage with application metrics such as traffic, latency, and error rates, and review application logs to identify the root cause. I also check for recent deployments or configuration changes. The resolution depends on the cause—it might involve scaling the application, rolling back a faulty release, optimizing the application, or right-sizing the infrastructure. Finally, I verify that CPU utilization has normalized and implement preventive measures such as improved Auto Scaling, monitoring, and performance tuning."**
