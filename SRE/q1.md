# LLM Infrastructure Auto Scaling – Interview Summary

## Project Overview

One of the key infrastructure projects I worked on was designing and implementing auto scaling for an LLM-based application running on AWS.

The application's primary objective was to answer user queries using Retrieval-Augmented Generation (RAG). A user's question first went through the application layer, which retrieved relevant documents from a vector database and then sent the context to an LLM for inference before returning the response.

The high-level architecture looked like this:

```
Users
   │
   ▼
Application Load Balancer (ALB)
   │
   ▼
Haystack Application Servers (EC2 Auto Scaling Group)
   │
   ├──► Embedding Service
   │
   ├──► Milvus Vector Database
   │
   └──► vLLM Inference Server (GPU)
                    │
                    ▼
              Response to User
```

The Haystack servers acted as the orchestration layer. They received requests from the ALB, retrieved relevant documents from Milvus, interacted with the embedding service when required, sent prompts to the vLLM inference server, and finally returned the generated response to the user.

My responsibility was to design the infrastructure, configure Auto Scaling Groups, create CloudWatch alarms, perform load testing, and determine the right scaling strategy for the application layer.

---

# The Challenge

Initially, we considered using CPU utilization as the scaling metric because that is the most common approach for Auto Scaling Groups.

However, after performing load testing, we realized CPU utilization did not accurately represent the application's workload.

The reason was that this application was not CPU-bound. It was latency-bound.

Each request involved several downstream operations before a response could be returned.

The request flow looked like this:

```
User Request
      │
      ▼
Haystack receives request
      │
      ▼
Query Milvus Vector Database
      │
      ▼
Wait for vector search
      │
      ▼
Call Embedding Service (if required)
      │
      ▼
Call vLLM GPU Server
      │
      ▼
Wait for LLM inference
      │
      ▼
Return response
```

Notice that during a significant portion of the request lifecycle, the Haystack server is waiting for downstream services.

For example:

* It sends a request to Milvus and waits for the response.
* It sends another request to the GPU inference server and waits again.
* Only small portions of the request involve active CPU processing.

Because of this waiting time, CPU utilization remained relatively low even when the application was handling a large number of concurrent user requests.

During our load tests, we observed situations where:

* CPU utilization stayed around 35–45%.
* Memory utilization remained stable.
* Response time increased significantly.
* Active requests continued to accumulate.
* Users started experiencing slower responses.

If Auto Scaling had relied only on CPU or memory, no new instances would have been launched because neither metric crossed the configured threshold.

This would have resulted in poor user experience despite the infrastructure appearing healthy.

That observation led us to rethink our scaling strategy.

---

# Why We Selected RequestCountPerTarget

Since every user request passed through the Application Load Balancer, CloudWatch already provided an ALB metric called **RequestCountPerTarget**.

This metric represents the average number of requests each healthy target (Haystack instance) receives.

Unlike CPU or memory, RequestCountPerTarget directly reflects application demand.

As more users access the application:

* More requests reach the ALB.
* The ALB distributes them across Haystack instances.
* The RequestCountPerTarget metric increases proportionally.

This makes it an excellent workload-based scaling metric.

Instead of asking, "How busy is the CPU?", we asked, "How much traffic is each application server handling?"

That approach aligned much better with the actual user workload.

---

# Determining the Scaling Threshold

Rather than selecting a threshold arbitrarily, we performed load testing to determine how much traffic the existing infrastructure could comfortably handle.

Our baseline infrastructure consisted of:

* 2 Haystack servers
* 1 vLLM GPU server

During testing, we observed that this configuration consistently handled approximately **60 requests every 10 seconds** while maintaining acceptable response times.

The next step was to convert this observation into a CloudWatch alarm threshold.

### Step 1 – Convert to requests per minute

CloudWatch evaluates ALB RequestCountPerTarget on a per-minute basis.

We converted:

```
60 requests / 10 seconds

×

6

=

360 requests / minute
```

This meant the ALB target group processed approximately **360 requests every minute**.

### Step 2 – Calculate requests per target

Since there were two Haystack instances behind the ALB:

```
360 requests / minute

÷

2 instances

=

180 requests / target / minute
```

Therefore, each Haystack server was processing approximately **180 requests per minute** under normal operating conditions.

This became our scale-out threshold.

---

# Auto Scaling Configuration

The Haystack Auto Scaling Group was configured approximately as follows:

```
Minimum Capacity : 2

Desired Capacity : 2

Maximum Capacity : 4
```

The CloudWatch alarm monitored the RequestCountPerTarget metric.

Whenever the metric exceeded approximately **180 requests per target per minute** for the configured evaluation period, the Auto Scaling Group launched one additional Haystack instance.

As traffic continued increasing, additional instances were launched until the configured maximum capacity was reached.

Similarly, when traffic reduced and remained below the lower threshold for a sustained period, instances were gradually removed to reduce infrastructure cost.

Cooldown periods and evaluation periods were configured to avoid scaling due to short traffic spikes.

---

# Example Scenario

Suppose traffic suddenly increases to:

```
720 requests/minute
```

With only two Haystack servers:

```
720

÷

2

=

360 requests/target/minute
```

This exceeds the configured threshold.

CloudWatch triggers the Auto Scaling policy.

A third Haystack server is launched.

Once the new instance becomes healthy, the ALB distributes traffic across three servers:

```
720

÷

3

=

240 requests/target/minute
```

Although the traffic remains high, the workload per instance is significantly reduced, improving response times and increasing overall system stability.

If demand continues to grow, another instance can be added until the Auto Scaling Group reaches its maximum configured capacity.

---

# Why We Didn't Use Memory Utilization

Memory usage remained relatively stable during testing.

The application did not continuously allocate large amounts of memory per request.

Instead, most request latency resulted from waiting for downstream services.

As a result, memory utilization did not accurately indicate increasing user demand and therefore was not suitable as the primary scaling metric.

---

# Real-World Learning

This project taught me an important SRE principle:

**Infrastructure metrics should not always drive scaling decisions.**

The scaling metric should represent the application's actual bottleneck.

For traditional web applications, CPU utilization may work well.

For streaming applications, queue length may be more appropriate.

For message-processing systems, consumer lag might be the right metric.

For our LLM application, RequestCountPerTarget best represented real user demand because it measured how much traffic each application server was handling.

# Possible Follow-Up Questions

### Q: Why didn't you use Target Tracking based on CPU?

Because CPU never reflected the real workload. The application spent much of its time waiting on Milvus and the GPU inference server. Scaling on CPU would have delayed instance launches even while users experienced increasing response times.

### Q: Why use RequestCountPerTarget instead of RequestCount?

RequestCount measures total traffic reaching the load balancer. RequestCountPerTarget divides that traffic by the number of healthy instances, allowing scaling decisions to be based on the load handled by each server rather than the total system traffic.

### Q: How did you decide on the threshold?

We derived it from load-testing results rather than guessing. Our baseline handled approximately 60 requests every 10 seconds. Converting that to requests per minute and dividing by the two Haystack instances gave us approximately 180 requests per target per minute.

### Q: Why not scale the GPU servers at the same time?

The application layer and inference layer had different bottlenecks. Haystack servers primarily handled orchestration, while GPU servers performed model inference. We treated them as separate scaling domains and evaluated each independently to avoid over-provisioning expensive GPU instances.

# Key Interview Takeaways

If I had to summarize this project in a few sentences during an interview, I would say:

> "In our LLM infrastructure, we found that CPU and memory utilization were poor indicators of application load because the Haystack servers spent a significant amount of time waiting for Milvus vector searches and GPU inference. Through load testing, we determined that two Haystack instances could comfortably process about 60 requests every 10 seconds. We converted that to 360 requests per minute and divided it across two instances, giving us a RequestCountPerTarget threshold of approximately 180 requests per minute. We configured CloudWatch alarms and an Auto Scaling Group to scale the Haystack layer based on this workload metric rather than CPU, which resulted in more responsive and efficient scaling under real user traffic."
