## Describe the VPC design you provisioned — how did you segment public/private subnets, and what's in each?


# VPC Design for the LLM Infrastructure – Interview Answer

In our LLM infrastructure, I provisioned a **highly available VPC spanning two Availability Zones**. The primary goal was to ensure high availability, secure network segmentation, and controlled internet access while keeping the application scalable.

The VPC was divided into **public and private subnets**, with each subnet serving a specific purpose.

The architecture looked like this:

```text
                    Internet
                        │
                        ▼
               Internet Gateway (IGW)
                        │
         ┌──────────────┴──────────────┐
         │                             │
         ▼                             ▼
  Public Subnet (AZ-1)         Public Subnet (AZ-2)
         │                             │
         ├──────────────┬──────────────┤
         │              │              │
         ▼              ▼              ▼
      ALB          NAT Gateway     NAT Gateway
         │
         ▼
─────────────────────────────────────────────────────
             Private Application Subnets
─────────────────────────────────────────────────────
         │                             │
         ▼                             ▼
 Haystack EC2 (ASG)             Haystack EC2 (ASG)
         │                             │
         └──────────────┬──────────────┘
                        │
                        ▼
                 vLLM GPU Instance
                        │
        ┌───────────────┴──────────────┐
        ▼                              ▼
Embedding Server               Milvus Database
```

---

# VPC CIDR

The VPC was created with a sufficiently large CIDR block so that additional application tiers could be added in the future without IP exhaustion. We then divided this CIDR into separate subnets across two Availability Zones for high availability.

---

# Public Subnets

Each Availability Zone contained one public subnet.

The public subnets contained only components that needed direct internet connectivity.

These included:

* Application Load Balancer (ALB)
* NAT Gateway
* Internet Gateway attachment

The public subnet route table contained:

```text
Destination        Target

0.0.0.0/0  --->  Internet Gateway
```

The ALB was internet-facing because it received requests from external users.

The NAT Gateway was also placed in the public subnet because it requires a public Elastic IP to provide outbound internet access to resources in private subnets.

No application servers were deployed in the public subnet.

---

# Private Application Subnets

The Haystack application servers were deployed inside private subnets.

These servers did not have public IP addresses.

Only the Application Load Balancer was allowed to communicate with them through the target group.

This provided an additional security layer because users could not directly SSH or access the application servers from the internet.

The Haystack servers were responsible for:

* Receiving requests from the ALB
* Querying Milvus
* Communicating with the embedding service
* Sending prompts to the vLLM inference server
* Returning the response

The private subnet route table contained:

```text
Destination        Target

0.0.0.0/0  --->  NAT Gateway
```

The NAT Gateway allowed the private instances to perform outbound operations such as:

* Downloading operating system updates
* Pulling Docker images
* Accessing package repositories
* Sending logs to monitoring services

while still preventing inbound internet access.

---

# GPU Inference Layer

The vLLM GPU instance was also deployed inside a private subnet.

Since it only accepted requests from the Haystack application servers, exposing it to the internet would have increased the attack surface unnecessarily.

Keeping it private also ensured that only trusted application servers could invoke the inference API.

---

# Embedding Service

The embedding service was deployed in the private network because it was an internal microservice.

It only communicated with Haystack and never received requests directly from users.

---

# Milvus Vector Database

The Milvus vector database was deployed in the private network as well.

It stored vector embeddings used for semantic search and Retrieval-Augmented Generation (RAG).

For security reasons, it was never exposed to the internet.

Only the Haystack servers were allowed to access Milvus through security group rules.

---

# Route Tables

We maintained separate route tables for public and private subnets.

### Public Route Table

```text
0.0.0.0/0  ---> Internet Gateway
```

Attached to:

* Public Subnet AZ-1
* Public Subnet AZ-2

---

### Private Route Table

```text
0.0.0.0/0  ---> NAT Gateway
```

Attached to:

* Private Application Subnets
* GPU Subnets
* Internal service subnets

This ensured that private resources could initiate outbound connections without being directly reachable from the internet.

---

# Security Groups

We implemented security groups based on the principle of least privilege.

### ALB Security Group

Allowed:

* HTTP (80)
* HTTPS (443)

Source:

```text
0.0.0.0/0
```

---

### Haystack Security Group

Allowed inbound traffic only from the ALB Security Group on the application port.

No direct internet access was permitted.

---

### vLLM Security Group

Allowed inbound traffic only from the Haystack Security Group.

No other resources could communicate directly with the inference server.

---

### Milvus Security Group

Allowed inbound traffic only from the Haystack application servers.

This ensured that database access remained restricted to the application layer.

---

# High Availability

To eliminate a single point of failure, we distributed the infrastructure across two Availability Zones.

The Application Load Balancer was deployed across both public subnets, and the Haystack Auto Scaling Group launched instances in both private application subnets.

If one Availability Zone became unavailable, the ALB would continue routing traffic to healthy instances in the remaining zone, maintaining application availability.

---

# Why We Used Public and Private Subnets

The main reason was security.

Only the load balancer needed to be publicly accessible.

All backend services—including the application servers, GPU inference servers, embedding service, and Milvus database—remained isolated in private subnets.

This reduced the attack surface while still allowing controlled outbound internet access through the NAT Gateway.

It also aligned with AWS security best practices for production workloads.

---

# Interview Summary

> "I designed the VPC using a multi-AZ architecture with separate public and private subnets. The public subnets hosted the internet-facing ALB and NAT Gateways, while the private subnets hosted the Haystack application servers, vLLM GPU instances, embedding service, and Milvus database. Public subnets routed traffic through the Internet Gateway, whereas private subnets used NAT Gateways for outbound internet access. Security Groups restricted communication so that only the ALB could reach the application layer, and only the application layer could communicate with the GPU servers and database. This design improved security, high availability, and scalability while following AWS networking best practices."



## What exactly did you own in the Jenkins→SonarQube integration — quality gates? Build-breaking thresholds?


# Jenkins → SonarQube Integration – Interview Answer

In our CI/CD pipeline, one of my responsibilities was integrating **Jenkins with SonarQube** so that every code change was automatically analyzed before it moved to the build and deployment stages.

The overall objective was to ensure that only code meeting the organization's quality standards was deployed to higher environments. Instead of waiting until testing or production to identify code quality issues, we wanted to catch them early in the pipeline.

The pipeline flow was:

**Developer commits code → Jenkins Pipeline starts → Build application → SonarQube analysis → Quality Gate validation → Docker image build → Push image to ECR → Update Helm charts → ArgoCD deploys to Kubernetes**

My role was to configure and maintain the Jenkins–SonarQube integration. I installed and configured the SonarQube server, integrated it with Jenkins using authentication tokens, configured the SonarScanner in Jenkins, and updated the Jenkins pipeline so that code analysis ran automatically after every successful build.

After the application was compiled, Jenkins triggered a SonarQube scan. The scanner analyzed the source code and uploaded the analysis report to the SonarQube server. However, the pipeline didn't immediately continue. Jenkins waited for SonarQube to process the report and return the **Quality Gate** result.

The Quality Gate acted as a checkpoint in the CI/CD pipeline. If the code met the predefined quality standards, the pipeline automatically continued to the Docker build and deployment stages. If the Quality Gate failed, Jenkins immediately stopped the pipeline, preventing the Docker image from being built and ensuring that poor-quality code was not deployed.

The Quality Gate typically evaluated metrics such as:

* Bugs
* Vulnerabilities
* Code Smells
* Code Duplication
* Maintainability Rating
* Reliability Rating
* Security Rating
* Test Coverage (where applicable)

One important point is that **I was responsible for integrating and enforcing the Quality Gate within the CI/CD pipeline, not for defining the coding standards themselves**. The development or architecture team usually owned the Quality Profiles and Quality Gate rules based on the organization's coding standards.

For example, if the agreed Quality Gate required:

* No blocker issues
* No critical vulnerabilities
* Maintainability Rating of A
* Reliability Rating of A

then Jenkins would automatically wait for the Quality Gate result. If any of these conditions were not met, the pipeline would fail, the Docker image would not be created, and the deployment stages would not execute. Developers would review the SonarQube report, fix the issues, commit the changes, and rerun the pipeline.

This integration significantly improved our CI/CD process because it shifted code quality validation to an early stage. Instead of discovering issues during deployment or testing, developers received immediate feedback after every commit. It reduced deployment failures, improved overall code quality, and ensured that only code meeting the organization's quality standards progressed to Kubernetes deployment.

### Interview Summary

> "My responsibility was to integrate SonarQube with Jenkins and make it a mandatory quality checkpoint in our CI/CD pipeline. I configured the SonarScanner, established secure communication between Jenkins and SonarQube, and updated the pipeline to wait for the Quality Gate result before continuing. If the Quality Gate passed, Jenkins built the Docker image and proceeded with deployment. If it failed, the pipeline stopped automatically, preventing low-quality code from reaching production. While the development team defined the Quality Gate rules, my responsibility was to ensure those rules were consistently enforced through the CI/CD pipeline."


## Tell me about a production issue you diagnosed end-to-end (build failure or K8s runtime error) — root cause, fix, prevention.

# Production Issue – Kubernetes ImagePullBackOff

One production issue I worked on was during a Kubernetes deployment where the application failed to start after a new release. Although the Jenkins pipeline completed successfully and ArgoCD synchronized the deployment, the application was unavailable because the pods never reached the **Running** state.

### Initial Observation

The first alert came from our deployment dashboard, where the application health showed as degraded after deployment.

My first step was to verify whether the issue was with the application itself or with the Kubernetes deployment.

I checked the pod status using:

```bash
kubectl get pods -n <namespace>
```

The output showed that the newly created pods were in the **ImagePullBackOff** state.

This immediately indicated that Kubernetes was unable to pull the container image rather than an application crash.

### Investigation

To understand the exact reason, I described one of the failing pods.

```bash
kubectl describe pod <pod-name> -n <namespace>
```

The Events section contained the actual error message, which indicated that Kubernetes could not pull the image from the container registry.

At this stage, I considered several possible causes:

* The image tag might not exist.
* The image repository could be incorrect.
* The cluster might not have permission to access the registry.
* There could be a network issue between the cluster and the registry.

Instead of assuming the cause, I verified each possibility one by one.

### Root Cause Analysis

I first confirmed that the Jenkins pipeline had completed successfully and that the Docker image had actually been pushed to Amazon ECR.

The image was present in ECR, so the build process was not the issue.

Next, I reviewed the Helm values file that ArgoCD was using for deployment.

I found that the image repository configured in the Helm chart did not match the actual ECR repository where Jenkins had pushed the image.

As a result, Kubernetes was trying to download an image that did not exist.

### Resolution

I updated the Helm values with the correct ECR repository and image tag.

After committing the changes, ArgoCD automatically synchronized the updated configuration.

Once the new deployment started, Kubernetes successfully pulled the image, created new pods, and all pods transitioned to the **Running** state.

I then verified:

* Pod health
* Application logs
* Kubernetes events
* Service endpoints
* Application accessibility

to ensure the deployment was completely healthy.

### Prevention

After resolving the issue, we implemented a few improvements to reduce the chances of similar problems occurring again.

First, we standardized image repository configuration so that Jenkins and the Helm charts referenced the same repository instead of maintaining separate values.

Second, we added validation to the CI/CD pipeline to verify that the expected image existed in Amazon ECR before updating the Helm chart.

Finally, we documented the deployment process and introduced a deployment checklist so image repository changes would be validated before production deployments.

### Key Learning

The biggest lesson from this incident was not to jump directly to a solution.

Instead, I followed a structured troubleshooting approach:

1. Identify where the failure occurred.
2. Collect evidence using Kubernetes commands.
3. Verify each possible cause systematically.
4. Identify the actual root cause.
5. Apply the fix.
6. Add preventive measures to avoid recurrence.

This approach helped us restore the application quickly while also improving the reliability of future deployments.
