# Compare Jenkins Push-Based CI/CD vs GitOps (ArgoCD)

In modern DevOps, both Jenkins and ArgoCD are important tools, but they solve different problems.

Jenkins is primarily responsible for **Continuous Integration (CI)**, such as building, testing, scanning, and packaging applications.

ArgoCD is a **GitOps Continuous Deployment (CD)** tool that continuously synchronizes the Kubernetes cluster with the desired state stored in Git.

In our project, we actually used both together because each tool has its own strengths.

---

# Traditional Jenkins Push-Based Deployment

In a traditional CI/CD pipeline, Jenkins performs both CI and CD.

The workflow looks like this:

```text
Developer
      │
      ▼
Git Push
      │
      ▼
Jenkins
      │
Checkout Code
      │
Build Application
      │
Run Unit Tests
      │
SonarQube Analysis
      │
Trivy Scan
      │
Build Docker Image
      │
Push Image to Amazon ECR
      │
kubectl apply
or
helm upgrade
      │
      ▼
Kubernetes Cluster
```

Notice that Jenkins directly connects to the Kubernetes cluster and deploys the application.

This is called a **push-based deployment** because Jenkins pushes the new version into the cluster.

---

# Challenges with Push-Based Deployments

While this approach works well, it introduces a few operational challenges.

### 1. Jenkins Needs Cluster Access

Jenkins requires Kubernetes credentials, such as a kubeconfig or service account token, with permission to deploy applications.

If Jenkins is compromised, an attacker could potentially deploy or modify workloads in the cluster.

---

### 2. Configuration Drift

Suppose someone manually changes a Deployment using:

```bash
kubectl edit deployment
```

The running cluster now differs from the Git repository.

Jenkins won't automatically detect this drift.

As a result:

* Git says one thing.
* The cluster is running something different.

This makes troubleshooting and auditing more difficult.

---

### 3. Limited Deployment Visibility

Although Jenkins shows whether the deployment command succeeded, it doesn't continuously monitor the application's desired state.

For example:

* A Pod may fail after deployment.
* Someone might accidentally delete a Deployment.
* A resource could be modified manually.

Jenkins has already completed its job and generally won't detect or correct those changes.

---

# GitOps with ArgoCD

GitOps changes this model.

Instead of Jenkins deploying directly into Kubernetes, **Git becomes the single source of truth**.

The workflow looks like this:

```text
Developer
      │
      ▼
Git Commit
      │
      ▼
Jenkins
      │
Build Application
      │
Run Tests
      │
SonarQube
      │
Trivy
      │
Build Docker Image
      │
Push Image to ECR
      │
Update Helm Chart/Image Tag
      │
Commit to Git Repository
      │
      ▼
Git Repository
      │
      ▼
ArgoCD
      │
Continuously Watches Git
      │
      ▼
Synchronizes Kubernetes Cluster
```

Notice the key difference:

**Jenkins no longer deploys directly to Kubernetes.**

Instead, Jenkins updates the Git repository, and ArgoCD continuously monitors that repository.

When ArgoCD detects a change, it pulls the updated manifests or Helm charts and applies them to the cluster.

This is known as a **pull-based deployment model**.

---

# Why Teams Migrate to GitOps

## 1. Git Becomes the Single Source of Truth

Every deployment is represented by a Git commit.

This provides:

* Complete version history
* Easy rollbacks
* Code review through pull requests
* Better auditing

Instead of asking:

> "What's running in production?"

We simply look at the Git repository.

---

## 2. Automatic Drift Detection

Suppose someone manually changes a Deployment using:

```bash
kubectl edit deployment
```

ArgoCD detects that the cluster no longer matches Git.

Depending on the configuration, it can:

* Report the drift.
* Automatically revert the manual change.
* Synchronize the cluster back to the desired state.

This keeps production consistent with Git.

---

## 3. Improved Security

Jenkins no longer requires broad administrative access to the Kubernetes cluster.

Only ArgoCD communicates with the cluster.

This reduces the attack surface and limits the number of systems holding cluster credentials.

---

## 4. Easy Rollback

Suppose Version 2 introduces a bug.

With GitOps, rollback is straightforward:

```text
Git

↓

Revert Commit

↓

ArgoCD detects change

↓

Cluster automatically returns

to previous version
```

There is no need to manually execute deployment commands.

---

## 5. Better Visibility

The ArgoCD dashboard provides a real-time view of:

* Application health
* Synchronization status
* Resource differences
* Deployment history

Operators can immediately see whether an application is:

* Healthy
* Progressing
* Out of Sync
* Degraded

---

# Why We Used Both Jenkins and ArgoCD

In our project, we didn't replace Jenkins with ArgoCD because they solve different problems.

Jenkins handled the **Continuous Integration** responsibilities:

* Building the application
* Running unit tests
* SonarQube analysis
* Trivy security scanning
* Building Docker images
* Pushing images to Amazon ECR

Once the image was built successfully, Jenkins updated the Helm chart with the new image tag and committed that change to the Git repository.

From that point onward, ArgoCD took over.

ArgoCD continuously monitored the Git repository, detected the updated Helm chart, synchronized the Kubernetes cluster, and performed the deployment.

This separation of responsibilities made the pipeline cleaner and more secure.

---

# Push vs Pull Comparison

| Feature                  | Jenkins Push Model | GitOps (ArgoCD)      |
| ------------------------ | ------------------ | -------------------- |
| Deployment Model         | Push               | Pull                 |
| Source of Truth          | Jenkins Job        | Git Repository       |
| Cluster Access           | Jenkins            | ArgoCD               |
| Drift Detection          | No                 | Yes                  |
| Automatic Reconciliation | No                 | Yes                  |
| Rollback                 | Manual deployment  | Git revert + sync    |
| Audit Trail              | Build history      | Git history + ArgoCD |

> "Traditional Jenkins-based deployments use a push model where Jenkins builds the application and deploys it directly to Kubernetes. While this works well, Jenkins needs cluster credentials and cannot automatically detect configuration drift. In a GitOps model, Git becomes the single source of truth. Jenkins is responsible only for CI tasks such as building, testing, scanning, and publishing the Docker image. It then updates the deployment manifests or Helm chart in Git. ArgoCD continuously watches the Git repository and synchronizes the Kubernetes cluster with the desired state. Teams migrate to GitOps because it improves security, provides automatic drift detection and reconciliation, simplifies rollbacks through Git history, and offers better visibility into application health and deployment status."



# How Does ArgoCD Reconcile Drift Between Git and the Kubernetes Cluster?

One of the biggest advantages of ArgoCD is its ability to continuously detect and reconcile **configuration drift**.

Before understanding reconciliation, it's important to understand what **configuration drift** means.

Configuration drift occurs when the actual state of resources running in the Kubernetes cluster differs from the desired state stored in Git.

Since Git is considered the **single source of truth** in a GitOps model, any difference between Git and the cluster is treated as drift.

For example, suppose our Git repository contains a Deployment with:

```yaml
replicas: 3
```

However, someone manually logs into the cluster and executes:

```bash
kubectl scale deployment haystack --replicas=5
```

Now the cluster has:

```yaml
replicas: 5
```

while Git still says:

```yaml
replicas: 3
```

This difference is called **configuration drift**.

---

# How ArgoCD Detects Drift

ArgoCD continuously watches two things:

1. The Git repository (desired state).
2. The Kubernetes cluster (live state).

At regular intervals, or when a webhook notifies it of a Git change, ArgoCD compares the manifests stored in Git with the actual Kubernetes resources running in the cluster.

Conceptually, the process looks like this:

```text
                Git Repository
             (Desired State)
                     │
                     │
              ArgoCD compares
                     │
                     ▼
          Kubernetes Cluster
             (Live State)
```

If both match exactly:

```text
Git

==

Cluster
```

the application status is shown as:

```text
Synced
Healthy
```

No action is required.

---

# What Happens When Drift Is Detected?

Suppose someone manually changes a Deployment.

Git contains:

```yaml
replicas: 3
```

Cluster contains:

```yaml
replicas: 5
```

ArgoCD compares both states and immediately detects that the Deployment no longer matches Git.

The application status changes to:

```text
OutOfSync
```

This immediately alerts operators that the cluster has drifted from the desired configuration.

---

# How Reconciliation Works

ArgoCD supports two synchronization modes.

## Manual Sync

In Manual Sync mode:

* ArgoCD detects the drift.
* Marks the application as **OutOfSync**.
* Waits for an operator to approve synchronization.

When the operator clicks **Sync** (or runs the equivalent CLI command), ArgoCD applies the manifests from Git and restores the cluster to the desired state.

For example:

Cluster:

```yaml
replicas: 5
```

Git:

```yaml
replicas: 3
```

After synchronization:

Cluster:

```yaml
replicas: 3
```

The application returns to the **Synced** state.

---

## Automatic Sync

In Automatic Sync mode, no manual intervention is required.

Once ArgoCD detects that the cluster no longer matches Git, it automatically applies the manifests stored in Git.

In our previous example:

Someone manually scales:

```bash
kubectl scale deployment haystack --replicas=5
```

Within a short time, ArgoCD detects the difference and reapplies the Deployment manifest from Git.

The Deployment is automatically restored to:

```yaml
replicas: 3
```

This ensures that the cluster always matches the desired configuration stored in Git.

---

# Self-Healing

One of the most powerful ArgoCD features is **self-healing**.

Suppose someone accidentally deletes a Deployment:

```bash
kubectl delete deployment haystack
```

The Deployment disappears from the cluster.

However, it still exists in Git.

ArgoCD detects that the resource defined in Git no longer exists in the cluster.

If **automatic sync with self-heal** is enabled, ArgoCD recreates the Deployment automatically.

No manual intervention is required.

This significantly improves operational reliability.

---

# Pruning

Another useful feature is **pruning**.

Suppose Git originally contained:

```text
Deployment A

Deployment B
```

Later, Deployment B is removed from Git.

Without pruning, Deployment B would continue running in the cluster even though it is no longer defined in the desired state.

If pruning is enabled:

* ArgoCD detects that Deployment B exists only in the cluster.
* It automatically deletes the resource.

This keeps the cluster clean and ensures it exactly matches the Git repository.

---

# Real Project Example

In our CI/CD pipeline, Jenkins handled the Continuous Integration process by building the application, running SonarQube analysis, performing Trivy scans, building the Docker image, and pushing it to Amazon ECR.

After the image was published, Jenkins updated the Helm chart with the new image tag and committed that change to the Git repository.

ArgoCD continuously monitored the Git repository. When it detected the updated Helm chart, it compared the desired state stored in Git with the live resources in the Kubernetes cluster. If differences were found, ArgoCD synchronized the cluster by applying the updated manifests.

This GitOps approach ensured that Git always represented the desired state of the environment. It also provided an audit trail through Git history and reduced the risk of configuration drift caused by manual changes.

---

# Why This Is Better Than Traditional Deployments

Without GitOps:

* Administrators can make manual changes.
* Nobody knows exactly what is running.
* Configuration drift accumulates over time.

With ArgoCD:

* Git is the single source of truth.
* Drift is detected automatically.
* Clusters remain consistent.
* Rollbacks are as simple as reverting a Git commit.
* Manual configuration changes do not become permanent.
