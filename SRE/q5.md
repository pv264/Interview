# Kubernetes: Deployment vs StatefulSet vs DaemonSet

In Kubernetes, **Deployment**, **StatefulSet**, and **DaemonSet** are all workload controllers that manage Pods. The difference lies in **how the Pods are created, identified, updated, and scheduled**.

When deciding which controller to use, I first ask three questions:

1. Does my application need a stable identity or persistent storage?
2. Should one Pod run on every node?
3. Is my application stateless or stateful?

The answers determine which controller is appropriate.

---

# 1. Deployment

A **Deployment** is used for **stateless applications**.

In a stateless application, any replica can handle any request because no user-specific data is stored inside the Pod. If one Pod fails, another Pod can immediately replace it without affecting the application.

Typical examples include:

* Spring Boot APIs
* Node.js applications
* React frontend
* Nginx
* Python Flask applications
* Haystack application servers in our LLM project

A Deployment manages ReplicaSets, which ensure the desired number of Pods are always running.

For example:

```text
Deployment
      │
      ▼
ReplicaSet
      │
 ┌────┼────┐
 ▼    ▼    ▼
Pod1 Pod2 Pod3
```

If Pod2 crashes:

```text
Pod2 ❌

↓

Deployment creates

Pod4 ✅
```

Notice that Kubernetes doesn't try to recover Pod2. It simply creates a new Pod with a different name because Pods are considered disposable.

### Advantages

* Easy horizontal scaling.
* Rolling updates.
* Rollbacks.
* Self-healing.
* Best for stateless workloads.

### Real Project Example

In our LLM project, the **Haystack application servers** were stateless. Any instance could process any incoming request, so we deployed them using a Deployment (or an Auto Scaling Group when running on EC2). If we migrated this application to Kubernetes, Deployment would be the appropriate controller because the application does not require stable identities or persistent storage.

---

# 2. StatefulSet

A **StatefulSet** is used for **stateful applications** where each Pod must have:

* A stable hostname.
* A stable network identity.
* Persistent storage.
* Ordered startup and shutdown.

Unlike Deployments, Pods in a StatefulSet are **not interchangeable**.

Suppose we have:

```text
Database Cluster

db-0

db-1

db-2
```

If `db-1` crashes, Kubernetes recreates **db-1**, not a new Pod with a random name.

It also reattaches the same Persistent Volume to that Pod.

This is important because databases cannot simply start with empty storage.

### StatefulSet Characteristics

* Stable Pod names (`db-0`, `db-1`, `db-2`).
* Stable DNS records.
* Persistent Volumes remain attached.
* Ordered deployment.
* Ordered termination.
* Ordered scaling.

### Common Use Cases

* MySQL
* PostgreSQL
* MongoDB
* Cassandra
* Kafka
* ZooKeeper
* Elasticsearch

If your application stores data locally or depends on stable identities, StatefulSet is the correct choice.

---

# 3. DaemonSet

A **DaemonSet** ensures that **exactly one Pod runs on every Kubernetes node**.

Instead of scaling based on replicas, Kubernetes automatically schedules one Pod per node.

For example:

```text
Cluster

Node1

Node2

Node3

DaemonSet

↓

Node1 → Pod

Node2 → Pod

Node3 → Pod
```

If a fourth node is added:

```text
Node4 joins

↓

DaemonSet automatically creates

Pod on Node4
```

If Node2 is removed, the corresponding Pod is also removed automatically.

### Common Use Cases

DaemonSets are typically used for infrastructure services rather than business applications.

Examples include:

* Fluentd
* Fluent Bit
* Promtail
* Node Exporter
* Datadog Agent
* New Relic Agent
* Security monitoring agents

These components need to run on every node to collect logs, metrics, or security events.

---

# Real-World Example

Suppose an organization has an e-commerce platform running on Kubernetes.

The architecture might look like this:

```text
Internet
    │
    ▼
Ingress
    │
    ▼
Frontend API
(Order Service)
(Product Service)

↓

Deployment
```

Each API is stateless, so Deployments are used.

The application stores data in PostgreSQL.

```text
PostgreSQL

↓

StatefulSet
```

PostgreSQL requires persistent storage and stable identities.

To collect logs from every node:

```text
Fluent Bit

↓

DaemonSet
```

Fluent Bit runs one Pod on every worker node and forwards logs to a centralized logging platform.

This demonstrates that a single Kubernetes cluster often uses all three controllers together.

---

# Comparison Table

| Feature            | Deployment             | StatefulSet           | DaemonSet                            |
| ------------------ | ---------------------- | --------------------- | ------------------------------------ |
| Best For           | Stateless applications | Stateful applications | Node-level services                  |
| Pod Identity       | Temporary              | Stable                | One Pod per node                     |
| Persistent Storage | Optional               | Usually required      | Usually not required                 |
| Scaling            | Replica count          | Replica count         | Automatically one per node           |
| Rolling Updates    | Yes                    | Ordered               | Yes                                  |
| Example            | APIs, Frontend         | Databases, Kafka      | Prometheus Node Exporter, Fluent Bit |

---

# How I Decide Which One to Use

My decision process is simple:

* If the application is **stateless**, I use a **Deployment**.
* If the application stores data or requires stable identities, I use a **StatefulSet**.
* If the application is an infrastructure component that should run on every Kubernetes node, I use a **DaemonSet**.

---

# Interview Summary

> "Deployment, StatefulSet, and DaemonSet are all Kubernetes workload controllers, but they serve different purposes. I use Deployments for stateless applications like REST APIs or web services because Pods are interchangeable and easy to scale. I use StatefulSets for stateful workloads such as databases or Kafka because they provide stable Pod identities, ordered deployment, and persistent storage. I use DaemonSets for infrastructure components like Fluent Bit or Node Exporter that need to run on every worker node. In production, it's common to use all three together—for example, Deployments for application services, StatefulSets for databases, and DaemonSets for monitoring and logging agents."



# How Do You Debug a Pod Stuck in CrashLoopBackOff or Pending?

Whenever I troubleshoot a Kubernetes issue, I follow a structured approach instead of assuming the cause.

The first thing I do is identify the **Pod status**, because different statuses indicate different categories of problems.

For example:

* **Pending** means Kubernetes has not been able to schedule the Pod onto a worker node.
* **CrashLoopBackOff** means the Pod was scheduled and started, but the application inside the container keeps crashing and Kubernetes is repeatedly trying to restart it.

Since these are two different failure scenarios, my troubleshooting approach is slightly different.

---

# Scenario 1: Pod Stuck in Pending

A Pod in the **Pending** state usually indicates that Kubernetes cannot place the Pod on any available worker node.

### Step 1 – Verify Pod Status

First, I check the Pod status.

```bash
kubectl get pods -n <namespace>
```

If the status shows **Pending**, I know the container hasn't started yet.

---

### Step 2 – Describe the Pod

Next, I describe the Pod to see Kubernetes events.

```bash
kubectl describe pod <pod-name> -n <namespace>
```

The **Events** section is one of the most important places to investigate because Kubernetes tells us exactly why the Pod couldn't be scheduled.

---

### Common Causes of Pending Pods

#### 1. Insufficient Resources

The most common reason is that the cluster doesn't have enough CPU or memory.

Example event:

```text
0/3 nodes are available:
Insufficient CPU
```

To verify node resources:

```bash
kubectl top nodes
```

or

```bash
kubectl describe node <node-name>
```

Resolution:

* Add more worker nodes.
* Scale the node group.
* Reduce Pod resource requests if they are unnecessarily high.

---

#### 2. Persistent Volume Not Available

Another common reason is an unbound Persistent Volume Claim.

Check:

```bash
kubectl get pvc
```

If the PVC status is **Pending**, the Pod cannot start because storage isn't available.

---

#### 3. Node Selector or Affinity Rules

Sometimes the Pod specifies:

* nodeSelector
* Node Affinity
* Taints and Tolerations

but no node satisfies those requirements.

The Events section usually contains messages such as:

```text
node(s) didn't match node selector
```

---

#### 4. Taints and Tolerations

If worker nodes are tainted and the Pod doesn't tolerate those taints, Kubernetes won't schedule it.

Check node taints:

```bash
kubectl describe node
```

---

#### 5. Image Pull Issues

Sometimes the scheduler places the Pod, but the image cannot be downloaded.

Although this often results in **ImagePullBackOff** rather than Pending, it's still worth checking the Events section for image-related errors.

---

# Scenario 2: Pod Stuck in CrashLoopBackOff

CrashLoopBackOff means Kubernetes successfully scheduled the Pod and started the container, but the application inside the container keeps crashing.

Kubernetes automatically restarts it, and after repeated failures, it enters the CrashLoopBackOff state.

---

### Step 1 – Check Pod Status

```bash
kubectl get pods
```

Example:

```text
my-app

CrashLoopBackOff
```

---

### Step 2 – Describe the Pod

```bash
kubectl describe pod my-app
```

Here I check:

* Restart Count
* Last State
* Exit Code
* Events

The exit code often gives valuable clues.

---

### Step 3 – Check Application Logs

The next step is to inspect the application logs.

```bash
kubectl logs my-app
```

If the container restarts quickly, I retrieve the logs from the previous instance.

```bash
kubectl logs my-app --previous
```

This is one of the most useful commands because it often shows the exact exception that caused the application to terminate.

---

### Common Causes of CrashLoopBackOff

#### Application Crash

The application itself may have failed because of:

* Null pointer exception
* Configuration error
* Missing dependency
* Syntax error
* Database connection failure

The logs usually identify the root cause.

---

#### Incorrect Environment Variables

Sometimes required environment variables are missing.

For example:

```text
DATABASE_URL not found
```

The application exits immediately after startup.

---

#### Wrong Secrets or ConfigMaps

The application may fail because:

* Secret not mounted
* ConfigMap missing
* Incorrect configuration

Verify:

```bash
kubectl get secrets
kubectl get configmaps
```

---

#### Liveness Probe Failures

Sometimes the application is healthy but starts slowly.

If the Liveness Probe starts checking too early, Kubernetes believes the application is unhealthy and repeatedly restarts it.

Verify:

```bash
kubectl describe pod
```

Look for:

```text
Liveness probe failed
```

Resolution:

Increase:

* initialDelaySeconds
* timeoutSeconds
* failureThreshold

---

#### Application Listening on Wrong Port

Suppose Kubernetes expects:

```text
Container Port

8080
```

but the application actually starts on:

```text
9090
```

The health checks fail, and Kubernetes restarts the container continuously.

---

#### Out of Memory (OOMKilled)

Sometimes the application exceeds its memory limit.

Check:

```bash
kubectl describe pod
```

Example:

```text
Last State

OOMKilled
```

Resolution:

Increase memory limits or optimize the application.

---

# My Troubleshooting Workflow

Whenever I troubleshoot Kubernetes issues, I follow the same sequence:

```text
1. kubectl get pods

↓

2. kubectl describe pod

↓

3. kubectl logs

↓

4. Check Events

↓

5. Verify resources

↓

6. Verify configuration

↓

7. Apply fix

↓

8. Verify application health
```

This systematic approach helps me identify the root cause instead of making assumptions.

---

# Real Project Example

In one of my Kubernetes deployments, the application Pods entered the **ImagePullBackOff** state after deployment. I started by checking the Pod status and then described the Pod to inspect the Events section. The error showed that Kubernetes couldn't pull the container image from Amazon ECR. I verified that Jenkins had successfully pushed the image, then reviewed the Helm values used by ArgoCD. The root cause was an incorrect image repository reference. After updating the Helm configuration and redeploying, Kubernetes successfully pulled the image, the Pods entered the Running state, and the application became healthy again. This experience reinforced the importance of checking Kubernetes Events first rather than assuming the cause.

---

# Interview Summary

> "When debugging a Kubernetes Pod, I first identify whether the issue is at the scheduling stage or the application stage. If the Pod is Pending, I inspect the Events section using `kubectl describe pod` to check for insufficient resources, unbound Persistent Volume Claims, node selectors, or taints. If the Pod is in CrashLoopBackOff, I inspect the Pod description, review the restart count and exit code, and then check the application logs using `kubectl logs` and `kubectl logs --previous`. I also verify ConfigMaps, Secrets, health probes, and resource limits. I follow a structured troubleshooting process—collect evidence, identify the root cause, implement the fix, and then verify that the application is healthy—rather than making assumptions."



# HPA vs VPA vs Cluster Autoscaler

Kubernetes provides different autoscaling mechanisms because there are different layers that may need to scale in a production environment.

Sometimes the application receives more traffic and needs more Pods.

Sometimes the existing Pods don't have enough CPU or memory.

Sometimes there aren't enough worker nodes in the cluster to schedule additional Pods.

These are three different problems, and Kubernetes provides three different solutions:

* **Horizontal Pod Autoscaler (HPA)** → Scales the **number of Pods**
* **Vertical Pod Autoscaler (VPA)** → Scales the **CPU and memory allocated to a Pod**
* **Cluster Autoscaler (CA)** → Scales the **number of worker nodes**

I think of it like this:

```text
Cluster
   │
   ├── Cluster Autoscaler
   │      ↑
   │   Adds/Removes Nodes
   │
   ├── Node
   │      │
   │      ├── Pod
   │      │     ↑
   │      │  Vertical Pod Autoscaler
   │      │
   │      ├── Pod
   │      │
   │      └── Pod
   │            ↑
   │     Horizontal Pod Autoscaler
```

---

# 1. Horizontal Pod Autoscaler (HPA)

The **Horizontal Pod Autoscaler** automatically increases or decreases the **number of Pod replicas** based on resource utilization or custom metrics.

It is most commonly used with **Deployments**.

For example:

Initially:

```text
Deployment

↓

2 Pods
```

As traffic increases:

```text
Deployment

↓

6 Pods
```

The application now handles more user requests because there are more replicas available.

HPA can scale based on metrics such as:

* CPU utilization
* Memory utilization
* Custom Metrics
* External Metrics (for example, request rate or queue length)

### Example

Suppose an API normally runs with two Pods.

During office hours, CPU utilization reaches 80%.

The HPA detects that CPU exceeds the configured target and automatically increases the number of replicas from:

```text
2 Pods

↓

4 Pods

↓

6 Pods
```

When traffic decreases later in the day, HPA gradually scales the replicas back down.

### When I Use HPA

I use HPA for **stateless applications** such as:

* REST APIs
* Spring Boot applications
* Node.js services
* Frontend applications

If our Haystack application were deployed on Kubernetes, HPA would be a good fit because multiple replicas can process requests independently. In our AWS deployment, we achieved similar horizontal scaling using an EC2 Auto Scaling Group driven by the ALB `RequestCountPerTarget` metric.

---

# 2. Vertical Pod Autoscaler (VPA)

The **Vertical Pod Autoscaler** does **not** create additional Pods.

Instead, it changes the **CPU and memory requests and limits** assigned to an existing Pod.

For example:

Initially:

```text
CPU

500m

Memory

512Mi
```

After VPA recommendations:

```text
CPU

1 vCPU

Memory

2Gi
```

The Pod becomes more powerful rather than creating additional replicas.

Because changing CPU or memory requests often requires recreating the Pod, VPA may restart Pods depending on its update mode.

### When I Use VPA

VPA is useful for applications that:

* Cannot scale horizontally easily.
* Have unpredictable resource requirements.
* Are under-provisioned or over-provisioned.

It also helps optimize costs by recommending the right amount of CPU and memory instead of relying on guesswork.

---

# 3. Cluster Autoscaler (CA)

The **Cluster Autoscaler** works at the **infrastructure level**.

Instead of scaling Pods, it scales **worker nodes**.

Suppose HPA increases replicas from:

```text
2 Pods

↓

10 Pods
```

But the cluster has only one worker node.

The scheduler attempts to place the new Pods but reports:

```text
Pending
```

because there isn't enough CPU or memory available on existing nodes.

The Cluster Autoscaler detects that Pods are unschedulable due to lack of capacity and requests the cloud provider to add another worker node.

For example:

Initially:

```text
Cluster

↓

2 Worker Nodes
```

After scaling:

```text
Cluster

↓

4 Worker Nodes
```

Once the new nodes join the cluster, Kubernetes schedules the previously Pending Pods onto them.

Similarly, when node utilization remains low for a sustained period, the Cluster Autoscaler can remove unnecessary nodes to reduce infrastructure costs.

### When I Use Cluster Autoscaler

I use it in cloud-managed Kubernetes clusters such as:

* Amazon EKS
* Google GKE
* Azure AKS

where worker nodes are managed by an Auto Scaling Group or an equivalent node pool.

---

# How They Work Together

These three components often work together in a production environment.

Imagine an e-commerce application during a sale.

### Step 1

Traffic increases.

CPU utilization reaches 80%.

The HPA increases replicas:

```text
2 Pods

↓

8 Pods
```

### Step 2

The Kubernetes scheduler tries to place the new Pods.

However, the cluster has only two worker nodes.

Several Pods remain in the **Pending** state.

### Step 3

The Cluster Autoscaler detects unschedulable Pods.

It launches two additional worker nodes.

### Step 4

The new nodes join the cluster.

The Pending Pods are scheduled successfully.

Now the application can handle the increased traffic.

---

# Can HPA and VPA Be Used Together?

Generally, I avoid using HPA and VPA together on the same workload when both are scaling based on CPU or memory because they can influence each other's decisions and lead to unstable scaling behavior.

A common approach is:

* Use **HPA** for stateless web applications.
* Use **VPA** for workloads that benefit from resource tuning and are not horizontally scalable.
* Use **Cluster Autoscaler** alongside HPA so the cluster can grow when additional Pods cannot be scheduled.

---

# Comparison Table

| Feature           | HPA                                     | VPA                                | Cluster Autoscaler                       |
| ----------------- | --------------------------------------- | ---------------------------------- | ---------------------------------------- |
| Scales            | Number of Pods                          | CPU & Memory of Pods               | Number of Worker Nodes                   |
| Trigger           | CPU, Memory, Custom or External Metrics | Resource recommendations and usage | Unschedulable Pods / Underutilized Nodes |
| Typical Use Case  | Stateless applications                  | Resource optimization              | Cluster capacity management              |
| Creates New Pods  | ✅ Yes                                   | ❌ No                               | ❌ No                                     |
| Adds Worker Nodes | ❌ No                                    | ❌ No                               | ✅ Yes                                    |

---

# Interview Summary

> "The key difference is the layer they scale. Horizontal Pod Autoscaler increases or decreases the number of Pod replicas based on metrics like CPU utilization or custom metrics, making it ideal for stateless applications. Vertical Pod Autoscaler adjusts the CPU and memory requests and limits of existing Pods, which is useful for workloads that don't scale horizontally or need resource optimization. Cluster Autoscaler operates at the infrastructure level by adding or removing worker nodes when Pods cannot be scheduled due to insufficient cluster capacity. In production, HPA and Cluster Autoscaler are commonly used together—HPA responds to application demand by creating more Pods, and Cluster Autoscaler ensures there are enough worker nodes to run those Pods."

# Rolling Update vs Blue-Green vs Canary Deployment

In modern CI/CD pipelines, the goal of a deployment strategy is to release a new application version with **minimal downtime and minimal risk**.

The three most common deployment strategies are:

* Rolling Update
* Blue-Green Deployment
* Canary Deployment

Each strategy balances **risk, deployment speed, and rollback capability** differently.

---

# 1. Rolling Update

A **Rolling Update** is the default deployment strategy in Kubernetes.

Instead of replacing all Pods simultaneously, Kubernetes gradually replaces the old Pods with new ones.

For example:

Initially:

```text
Version 1

Pod1
Pod2
Pod3
Pod4
```

When deploying Version 2:

```text
Step 1

Pod1(v1) → Pod1(v2)

Step 2

Pod2(v1) → Pod2(v2)

Step 3

Pod3(v1) → Pod3(v2)

Step 4

Pod4(v1) → Pod4(v2)
```

At every stage, some Pods continue serving traffic while others are being updated.

This ensures:

* Zero downtime
* Continuous availability
* Automatic rollout through Kubernetes

### Advantages

* Simple to implement.
* No additional infrastructure required.
* Default Kubernetes deployment strategy.
* Suitable for most stateless applications.

### Limitations

If a bug exists in the new version, users may start experiencing issues before the rollout completes.

Although Kubernetes allows rollback, some production traffic has already reached the faulty version.

---

# 2. Blue-Green Deployment

Blue-Green deployment maintains **two identical production environments**.

Example:

```text
Blue Environment

Version 1

(Current Production)
```

```text
Green Environment

Version 2

(Not receiving traffic)
```

The new version is deployed completely into the Green environment.

After validation:

```text
Load Balancer

Blue

↓

Green
```

Traffic switches instantly.

If any issue occurs:

```text
Green

↓

Blue
```

Rollback is immediate because the previous environment is still running.

### Advantages

* Very fast rollback.
* No partially upgraded users.
* Easy production validation before traffic switch.

### Limitations

* Requires duplicate infrastructure.
* Higher operational cost.
* Not always practical for GPU-heavy applications because maintaining two complete inference environments can be expensive.

---

# 3. Canary Deployment

A Canary deployment releases the new version **to a small percentage of users first** instead of everyone.

For example:

Initially:

```text
100%

↓

Version 1
```

Deploy Version 2:

```text
90%

↓

Version 1

10%

↓

Version 2
```

If monitoring shows:

* No increase in errors
* Stable latency
* Healthy Pods
* Acceptable CPU and memory

Then gradually increase traffic:

```text
80 / 20

↓

50 / 50

↓

20 / 80

↓

100%

Version 2
```

If any issue appears:

Traffic immediately returns to Version 1.

Only a small percentage of users experience the issue.

This makes Canary the safest deployment strategy for production.

---

# Comparison

| Feature               | Rolling Update | Blue-Green            | Canary                 |
| --------------------- | -------------- | --------------------- | ---------------------- |
| Downtime              | None           | None                  | None                   |
| Infrastructure Cost   | Low            | High                  | Medium                 |
| Rollback              | Moderate       | Very Fast             | Very Fast              |
| Risk                  | Medium         | Low                   | Very Low               |
| Production Validation | Limited        | Before traffic switch | During gradual rollout |

---

# How Would I Implement Canary on Kubernetes?

There are multiple approaches.

The simplest method is to create **two Deployments**.

Deployment A:

```text
application-v1
```

Deployment B:

```text
application-v2
```

Both expose the same Service.

Initially:

```text
Version 1

9 Pods
```

```text
Version 2

1 Pod
```

The Kubernetes Service distributes requests approximately according to the number of healthy Pods.

So roughly:

```text
90%

↓

Version 1

10%

↓

Version 2
```

After monitoring:

Increase Version 2:

```text
Version 1

8 Pods

Version 2

2 Pods
```

Then:

```text
5 Pods

5 Pods
```

Eventually:

```text
0 Pods

10 Pods
```

This is a basic Kubernetes canary implementation.

# Canary Using Argo Rollouts (Recommended)

In production, I would prefer **Argo Rollouts** instead of manually changing replica counts.

Argo Rollouts extends Kubernetes Deployments and provides advanced deployment strategies.

The process looks like this:

```text
Developer

↓

Git Commit

↓

Jenkins

↓

Build Docker Image

↓

Push to Registry

↓

Update Helm Chart

↓

Git Repository

↓

ArgoCD Sync

↓

Argo Rollouts

↓

Canary Deployment
```

With Argo Rollouts, we can define rollout steps such as:

* Route 10% of traffic to Version 2.
* Pause for 5 minutes.
* Verify application health.
* Increase traffic to 25%.
* Pause again.
* Increase to 50%.
* Finally shift 100% of traffic.

During each step we monitor:

* Error rate
* Response time
* CPU utilization
* Memory utilization
* Application logs
* Business metrics

If any metric crosses the configured threshold, Argo Rollouts can automatically stop the rollout or roll back to the previous version.

---

# Monitoring During Canary

A Canary deployment is only successful if it is monitored carefully.

I would monitor:

* HTTP 5xx errors
* Application latency
* Pod restart count
* Kubernetes events
* CPU and memory utilization
* Prometheus alerts
* Grafana dashboards
* Application logs
* User-facing business metrics such as successful requests

If any of these metrics indicate degradation, I would stop the rollout and restore traffic to the stable version.

---

# Real Project Perspective

In our Kubernetes deployments, we used **Helm** for packaging applications and **ArgoCD** for GitOps-based continuous deployment. ArgoCD continuously watched the Git repository and synchronized the cluster whenever Helm chart changes were committed. For normal releases, we relied on Kubernetes rolling updates. If we wanted to reduce deployment risk for a critical release, I would implement canary deployments using **Argo Rollouts** integrated with ArgoCD, because it provides controlled traffic shifting, automated pauses, health analysis, and rollback capabilities while keeping Git as the single source of truth.
