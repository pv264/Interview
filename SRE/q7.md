# SRE Fundamentals: SLI, SLO, SLA, and Error Budgets

I remember these concepts by asking four simple questions:

* **SLI (Service Level Indicator):** How is the service *actually* performing?
* **SLO (Service Level Objective):** What reliability target have we set *internally*?
* **SLA (Service Level Agreement):** What commitment have we made to *customers* (and what are the penalties if it's not met)?
* **Error Budget:** What is the amount of failure we are *allowed* to have while still meeting our SLO?

## How We Use the Error Budget

The Error Budget is a practical tool used to decide whether to push new features or temporarily focus on system reliability:

* **If plenty of budget remains:** We continue with normal deployments and feature releases.
* **If the budget is almost exhausted:** We slow down or pause releases to focus entirely on improving stability until the service recovers.


# Metrics vs Logs vs Traces – How They Help in Root Cause Analysis

Whenever I'm troubleshooting a production issue, I don't rely on just one source of information. I use **metrics, logs, and traces together** because each answers a different question.

I like to think of them this way:

* **Metrics tell me *that* something is wrong.**
* **Logs tell me *what* went wrong.**
* **Traces tell me *where* it went wrong.**

Together, they give me the complete picture.

---

# 1. Metrics – "Is there a problem?"

Metrics are numerical values collected continuously over time.

Examples include:

* CPU utilization
* Memory usage
* Request rate
* Error rate
* Response latency
* Disk utilization
* Network traffic

Metrics are usually visualized in tools like **Prometheus and Grafana**.

Suppose our application normally receives:

```text
100 Requests/Second
```

Suddenly the dashboard shows:

```text
Response Time

200 ms

↓

2 seconds
```

At the same time,

the error rate increases from:

```text
1%

↓

12%
```

Immediately I know something is wrong.

But metrics don't tell me **why**.

They only tell me:

> "There is a problem."

Think of metrics like the dashboard in your car.

If the engine temperature suddenly rises, the dashboard warns you that something is wrong, but it doesn't explain the cause.

---

# 2. Logs – "What exactly happened?"

Once I know there is a problem, the next step is to examine the application logs.

Logs provide detailed information about what the application was doing.

For example:

```text
Database Connection Timeout

Order ID : 10234

Time : 10:35:21

Connection refused
```

Now I know exactly what happened.

Maybe:

* Database connection failed.
* Authentication failed.
* Null pointer exception occurred.
* Configuration was incorrect.
* API returned HTTP 500.
* Kubernetes health check failed.

Logs provide detailed error messages that metrics cannot.

Think of logs like a doctor's report after an X-ray.

The report tells you exactly what was found.

---

# 3. Traces – "Where did the request fail?"

Modern applications usually consist of multiple microservices.

For example:

```text
Client

↓

API Gateway

↓

Order Service

↓

Payment Service

↓

Inventory Service

↓

Database
```

A single user request may travel through several services before completing.

If the request takes:

```text
5 Seconds
```

Which service caused the delay?

Metrics can't tell me.

Logs from one service can't tell me the complete journey.

This is where distributed tracing helps.

A trace follows one request across every service.

Example:

```text
Client

↓

API Gateway

100 ms

↓

Order Service

150 ms

↓

Payment Service

4 Seconds

↓

Inventory

50 ms
```

Now it's immediately obvious that the Payment Service is responsible for the delay.

Without tracing, I might waste time checking every microservice individually.

---

# How They Work Together During an Incident

Suppose users report:

> "The application is very slow."

### Step 1 – Check Metrics

I first open Grafana.

I notice:

* CPU is normal.
* Memory is normal.
* Request latency has increased significantly.
* Error rate is rising.

Metrics tell me:

> There is definitely a production issue.

But they don't explain why.

---

### Step 2 – Check Traces

Next, I open the distributed tracing dashboard.

I select one slow request.

The trace shows:

```text
API Gateway

↓

50 ms

↓

Order Service

↓

80 ms

↓

Payment Service

↓

3.5 Seconds
```

Now I know exactly which service is slow.

Instead of investigating ten services, I focus only on the Payment Service.

---

### Step 3 – Check Logs

Now I open the logs for the Payment Service.

The logs show:

```text
Connection Timeout

Payment Database
```

Now I have identified the root cause.

The Payment Service was waiting for the database.

---

### Final Conclusion

So the complete troubleshooting process becomes:

```text
Metrics

↓

Something is wrong

↓

Traces

↓

Where is it happening?

↓

Logs

↓

What exactly failed?
```

This structured approach helps reduce the time required to identify the root cause.

---

# Real Project Example

In our Kubernetes environment, we used monitoring dashboards to observe infrastructure and application metrics such as CPU utilization, memory usage, request throughput, and latency. During an incident, metrics would first indicate that something was abnormal—for example, increased response time or error rates. We would then review the application logs to identify specific exceptions or failures. If the application consisted of multiple interacting services, distributed tracing would help identify which service introduced the delay. Using these three observability pillars together allowed us to move from symptom to root cause much faster than relying on a single data source.

# How Would You Design a Monitoring Stack for a New Microservice?

Whenever I design a monitoring solution for a new microservice, I don't start with the tools. I first identify **what information I need to know to determine whether the service is healthy**.

A monitoring stack should answer four questions:

1. **Is the service receiving traffic?**
2. **Is it responding quickly?**
3. **Is it returning errors?**
4. **Is it running out of resources?**

These are Google's **Four Golden Signals**:

* **Latency**
* **Traffic**
* **Errors**
* **Saturation**

Once I know what to measure, I choose the appropriate tools to collect, visualize, and alert on those metrics.

---

# High-Level Monitoring Architecture

A typical monitoring architecture would look like this:

```text
                    Microservice
                         │
        ┌────────────────┼────────────────┐
        │                │                │
        ▼                ▼                ▼
   Metrics          Application Logs   Traces
        │                │                │
        ▼                ▼                ▼
  Prometheus          Loki / ELK      Jaeger / Tempo
        │                │                │
        └────────────────┼────────────────┘
                         │
                         ▼
                     Grafana
                         │
                         ▼
                    Alertmanager
                         │
               Email / Slack / PagerDuty
```

Every component has a specific responsibility.

* **Prometheus** collects metrics.
* **Loki or ELK** stores logs.
* **Jaeger or Tempo** stores distributed traces.
* **Grafana** provides dashboards.
* **Alertmanager** sends alerts to the operations team.

---

# Step 1 – Monitor Traffic

The first thing I monitor is **traffic**.

This tells me whether users are reaching the application.

Typical metrics include:

* Requests per second (RPS)
* Requests per minute
* Active connections
* Incoming network traffic

Example:

Normally:

```text
120 Requests/sec
```

Suddenly:

```text
5 Requests/sec
```

This immediately tells me something has changed.

Maybe:

* Load balancer issue
* DNS problem
* Application unavailable
* Network failure

Without traffic metrics, I may not even realize users have stopped reaching the service.

---

# Step 2 – Monitor Latency

The second golden signal is **latency**.

Receiving requests isn't enough.

The application must respond quickly.

I would monitor:

* Average response time
* P95 latency
* P99 latency

Why P95 or P99?

Because averages can hide problems.

For example:

Average latency:

```text
150 ms
```

Looks healthy.

But:

```text
P99

3 Seconds
```

This means 1% of requests are extremely slow.

Those users still experience poor performance.

For production systems, percentile-based latency is much more useful than averages.

---

# Step 3 – Monitor Errors

Next, I monitor the error rate.

Typical metrics include:

* HTTP 5xx responses
* HTTP 4xx responses
* Exception count
* Failed requests
* Database failures

Suppose:

Normally:

```text
Error Rate

0.2%
```

Suddenly:

```text
8%
```

Even if CPU usage is low, an increasing error rate indicates users are experiencing failures.

This is one of the highest-priority alerts because it directly impacts customers.

---

# Step 4 – Monitor Saturation

The fourth golden signal is **saturation**.

Saturation tells me whether the system is approaching its capacity limits.

Infrastructure metrics include:

* CPU utilization
* Memory utilization
* Disk usage
* Network bandwidth
* Disk I/O

Application metrics include:

* Thread pool utilization
* Connection pool usage
* Queue length
* Database connection count

For Kubernetes, I also monitor:

* Pod CPU usage
* Pod memory usage
* Node CPU utilization
* Node memory utilization
* Restart count
* Pending Pods

These metrics help identify bottlenecks before they cause outages.

---

# Kubernetes Monitoring

If the microservice runs on Kubernetes, I also monitor the platform itself.

For example:

### Pod Health

* Running Pods
* Pending Pods
* CrashLoopBackOff
* Restart Count

### Deployment Status

* Available Replicas
* Unavailable Replicas
* Rollout Status

### Node Health

* Node Ready
* Disk Pressure
* Memory Pressure
* CPU Pressure

### HPA Metrics

* Current CPU
* Desired Replicas
* Scaling Events

This ensures I can quickly determine whether the issue is in the application or the Kubernetes infrastructure.

---

# Logging

Metrics tell me **that** something is wrong.

Logs tell me **what** went wrong.

I collect:

* Application logs
* Access logs
* Error logs
* Kubernetes logs

Examples:

* Database timeout
* Null Pointer Exception
* Authentication failure
* Configuration error

Logs help identify the exact root cause.

---

# Distributed Tracing

If the application consists of multiple microservices, I also enable distributed tracing.

Suppose a request flows like this:

```text
API Gateway

↓

Order Service

↓

Payment Service

↓

Inventory Service
```

Tracing allows me to identify exactly where the delay occurred.

Without tracing, I would have to inspect every service individually.

---

# Dashboards

In Grafana, I would build dashboards for different audiences.

### Infrastructure Dashboard

* CPU
* Memory
* Disk
* Network

### Kubernetes Dashboard

* Node Health
* Pod Status
* Restart Count
* Deployments

### Application Dashboard

* Requests/sec
* Latency
* Error Rate
* Response Time

### Business Dashboard

* Successful Orders
* Failed Orders
* Active Users
* Transactions

This gives both engineers and stakeholders visibility into the health of the platform.

---

# Alerting Strategy

Monitoring without alerts is incomplete.

I configure alerts only for actionable conditions.

Examples:

Critical:

* Service unavailable
* High HTTP 5xx error rate
* Pod CrashLoopBackOff
* Node Not Ready

Warning:

* CPU above 80%
* Memory above 85%
* Disk usage above 80%
* High latency
* High restart count

Alerts are routed through Alertmanager to Slack, email, or PagerDuty based on severity.

To reduce alert fatigue, I configure evaluation periods so alerts are triggered only if a condition persists for several minutes rather than during brief spikes.

---

# Real Project Example

In our Kubernetes environment, we monitored infrastructure and application health using Prometheus and Grafana. We tracked CPU, memory, request throughput, latency, and pod health, while Alertmanager notified the team when critical thresholds were exceeded. During incidents, we correlated metrics with application logs to identify the root cause, and for distributed workflows we relied on tracing to determine which service introduced latency. This combination of metrics, logs, and traces gave us end-to-end observability across the platform.

---

# Interview Summary

> "When designing a monitoring stack, I first identify what needs to be monitored rather than starting with the tools. I focus on the four golden signals: traffic, latency, errors, and saturation. I use Prometheus to collect infrastructure and application metrics, Grafana for dashboards, Alertmanager for notifications, Loki or ELK for centralized logging, and Jaeger or Tempo for distributed tracing. For Kubernetes, I also monitor pod health, node health, deployments, and autoscaling metrics. Finally, I create meaningful alerts with appropriate thresholds and evaluation periods so the operations team is notified only about actionable issues. This approach provides complete observability and helps detect and resolve production issues before they significantly impact users."



# Production Incident (STAR Format) – LLM Application Performance Issue Due to Auto Scaling

## Situation

In one of our LLM projects, users started reporting that the application was becoming slow during peak traffic hours. The application was still available, but response times had increased significantly, and some requests were timing out.

Our application architecture consisted of an Application Load Balancer, Haystack application servers running in an Auto Scaling Group, a vLLM inference server, an embedding service, and a Milvus vector database.

---

## Task

My responsibility was to identify the bottleneck, restore application performance, and ensure the infrastructure could automatically handle similar traffic spikes in the future.

---

## Action

### Step 1 – Detection

The issue was detected through our CloudWatch dashboards.

I observed that:

* Application response time had increased.
* The number of requests reaching the ALB had increased significantly.
* Users were reporting slow responses.

The first step was to determine whether this was an infrastructure issue or an application issue.

---

### Step 2 – Investigation

I started by checking the health of the EC2 instances behind the Application Load Balancer.

The instances were healthy.

Next, I reviewed CloudWatch metrics.

Interestingly, CPU utilization was only around **40–50%**, but the **RequestCountPerTarget** metric had increased considerably.

This indicated that the application servers were handling more requests than usual, even though CPU utilization remained relatively low.

I knew that our Haystack application spends much of its time waiting for downstream services such as Milvus and the vLLM inference server. Because of this, CPU utilization wasn't accurately representing the actual workload.

That confirmed that CPU was not the right scaling metric for this application.

---

### Step 3 – Root Cause

The Auto Scaling Group was originally configured to scale based only on CPU utilization.

Since CPU never crossed the configured threshold, the Auto Scaling Group didn't launch additional instances, even though request volume and response times were increasing.

The actual bottleneck was the number of requests being handled by each Haystack instance.

---

### Step 4 – Resolution

Based on our load-testing results, we knew that two Haystack instances could comfortably handle about **60 requests every 10 seconds**.

We converted that into a CloudWatch threshold:

* 60 requests per 10 seconds = 360 requests per minute.
* Two instances meant each instance could handle approximately **180 requests per minute**.

We updated the Auto Scaling policy to use the ALB **RequestCountPerTarget** metric instead of CPU utilization.

Now, whenever the request count per instance exceeded the threshold for a sustained period, the Auto Scaling Group automatically launched another Haystack instance.

After the additional instances came online, the ALB distributed traffic across more servers, response times improved, and the application returned to normal performance.

---

## Result

The application performance improved significantly during peak traffic.

Instead of manually increasing capacity whenever traffic grew, the infrastructure automatically scaled based on real user demand.

This reduced response times, improved user experience, and avoided unnecessary scaling during normal traffic periods.

---

## Prevention

After resolving the issue, we made a few improvements:

* We permanently switched the Auto Scaling policy from CPU-based scaling to **RequestCountPerTarget**.
* We validated the thresholds using load-testing results rather than guessing.
* We configured CloudWatch alarms to notify the team when request volume increased.
* We documented the scaling strategy so future deployments followed the same approach.

---

# What I Learned

This incident taught me that choosing the **right metric** is just as important as enabling Auto Scaling.

For distributed applications, CPU isn't always the best indicator of load. In our case, request volume per application server represented the workload much more accurately, leading to better scaling decisions and improved application performance.

---
